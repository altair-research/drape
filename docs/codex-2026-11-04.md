## A. WebKit 실패 5건 원인 조사

```text
저장소: altair-research/drape (로컬 C:\dev\drape). 공개 저장소다 — 이메일·키·비밀번호를 파일에 쓰지 마라.
C:\dev\drape 의 체크아웃·브랜치는 바꾸지 마라. 먼저:
  git -C C:\dev\drape fetch origin
  git -C C:\dev\drape worktree add C:\dev\drape-codex-a -b codex/webkit-diagnose origin/main
그 폴더(C:\dev\drape-codex-a)에서만 일한다. 이 저장소에만 git config user.name "altair research lab", user.email "altair.research.lab@gmail.com".

배경: tests/e2e/REPORT.md — Playwright 34건 중 WebKit 영어에서 5건 실패(합성 이미지 준비 중 naturalWidth 대기 30초 초과 1건, 이어서 "Target page, context or browser has been closed" 페이지 생성 실패 4건). Chromium 은 전부 통과, WebKit 한국어도 통과. 원인은 아직 모른다.

할 일: 원인을 가려 낸다. index.html·sw.js 는 고치지 마라.
1) 재현: npm install → npx playwright install webkit → WebKit 만, workers=1, 실패한 테스트 하나씩(--grep) 그리고 전체로. 각각 3번씩 돌려 재현율을 표로.
2) 갈라 보기: 한/영 순서 바꾸기, 테스트마다 새 브라우저(launch) vs 새 컨텍스트, 합성 PNG 크기 줄이기(800×1000 → 400×500), 이미지 준비 대기를 naturalWidth 대신 img.decode() 로, 타임아웃 60초. 어떤 조건에서 사라지는지.
3) 결론을 셋 중 하나로: (가) 테스트 도구/실행 환경 문제 → tests/e2e/ 의 테스트·helpers 만 고쳐 안정화(skip·재시도 추가 금지, 원인을 없애는 방식으로), (나) 앱 문제(예: 사진 불러오기 경로가 WebKit 에서 멈춤) → 고치지 말고 최소 재현 절차와 의심 코드 줄 번호, (다) 모름 → 시도한 것과 남은 가설.
4) 마지막에 전체 테스트(app.spec.js + mobile.spec.js, Chromium + WebKit)를 돌려 통과/실패 표.
보고서: tests/e2e/WEBKIT-DIAG.md — 재현율 표, 결론(확신도: 확실/추정/모름), 바꾼 테스트 파일 목록과 이유. 스크린샷·trace 는 커밋하지 마라.

Git: 브랜치 codex/webkit-diagnose 에서 커밋. 커밋 메시지에 AI 공동저자 줄을 넣지 마라. main 에 병합·푸시하지 마라(main 이 곧 운영 사이트다). 브랜치는 푸시해도 된다. 끝나면 git worktree remove 로 폴더를 정리해도 된다(브랜치는 남긴다).
끝나면 세 줄로 보고: 브랜치 · 결론(가/나/다) · 전체 통과/실패 수.
```

## B. 출시 전 점검 테스트 (오프라인·캐시·manifest·assetlinks·링크)

```text
저장소: altair-research/drape (로컬 C:\dev\drape). 공개 저장소다 — 이메일·키·비밀번호를 파일에 쓰지 마라.
C:\dev\drape 의 체크아웃·브랜치는 바꾸지 마라. 먼저:
  git -C C:\dev\drape fetch origin
  git -C C:\dev\drape worktree add C:\dev\drape-codex-b -b codex/release-checks origin/main
그 폴더(C:\dev\drape-codex-b)에서만 일한다. 이 저장소에만 git config user.name "altair research lab", user.email "altair.research.lab@gmail.com".

배경: 앱은 GitHub Pages /drape/ 에서 도는 PWA(index.html 한 파일 + sw.js), 안드로이드 Play 앱은 이 사이트를 그대로 띄우는 TWA 다. 사이트를 고칠 때 index.html 의 APP_VERSION 과 sw.js 의 VERSION("drape-vNN")을 함께 올리는 규칙이 있다. 이 규칙이 실제로 새 파일을 받게 만드는지 테스트가 없다.

할 일: tests/e2e/release.spec.js (Chromium 만 — 서비스워커는 이 테스트에서만 허용) 와 tools/check-release.mjs (Node, 외부 패키지 없이). index.html·sw.js 는 고치지 마라(문제는 보고만).
release.spec.js:
 1) 서비스워커 설치 → 네트워크 끊고(context.setOffline(true)) 새로고침해도 화면이 뜨고 #ver 가 같다.
 2) 캐시 교체: 임시 폴더에 사이트를 복사해 서버로 띄우고, 첫 방문 → 복사본의 APP_VERSION·VERSION 숫자를 1 올림 → 다시 방문(필요하면 새로고침 1~2회) → 새 #ver 가 보이고 caches.keys() 에 옛 drape- 캐시가 남지 않는지. 저장소 파일 자체는 건드리지 않는다.
 3) 사진 모드 경로가 오프라인에서도 되는지(합성 canvas 이미지만, 사람 사진 금지).
tools/check-release.mjs (콘솔 표 + 종료 코드):
 - APP_VERSION 숫자 == sw.js VERSION 숫자, 캐시 이름 접두사 drape-.
 - manifest(있는 파일 경로를 index.html 에서 찾음): name·short_name·start_url·scope·display·icons — 아이콘 파일이 있고 실제 픽셀 크기가 적힌 sizes 와 같은지(PNG 헤더로), 192·512 와 maskable 유무.
 - .well-known/assetlinks.json(있으면): JSON 형식, relation·package_name·sha256_cert_fingerprints 형식(콜론 구분 32바이트). 값은 공개 정보지만 보고서에 지문 전체를 다시 적지는 마라.
 - index.html 과 저장소 안 html 의 상대 링크·이미지가 실제 파일로 있는지, 외부 링크는 목록만(요청 보내지 않음).
보고서: docs/RELEASE-CHECK.md — 항목별 통과/실패, 문제와 제안(확신도: 확실/추정/모름), 실행법 3줄.

Git: 브랜치 codex/release-checks 에서 커밋. 커밋 메시지에 AI 공동저자 줄을 넣지 마라. main 에 병합·푸시하지 마라. 브랜치는 푸시해도 된다.
끝나면 세 줄로 보고: 브랜치 · 통과/실패 수 · 꼭 봐야 할 문제 하나.
```
